# 来源文档分析与通用化说明

## AGENTS.md

- 定位：项目级硬约束与协作入口。
- 可复用部分：先拆分任务并确认；一次只做一个编号任务；按设计、数据模型、架构执行；完成后更新进度；禁止泄露密钥、提交环境文件、越过后端访问数据库；记忆库是权威来源。
- 不应硬编码：OwnerWeb 名称、React/Cloudflare 目录、`src/services/` 规则、管理员/评论/前端等特定业务，以及 Agentrouter/GLM 纯文本和禁止浏览器的代理限制。后者只在目标项目明确采用该代理时写入。

## memory-bank/PRD.md

- 定位：产品目标、用户、场景、页面/功能范围、已实现能力和验收标准。
- 新项目用途：先记录批准的产品范围和可观察验收，不把实现细节放进来。
- OwnerWeb 特例：个人作品集、访客评论、管理员后台、博客、3D PCB、Cloudflare 部署均不能照搬。

## DESIGN.md

- 定位：界面或交互效果基准，包括视觉、布局、状态、响应式、无障碍和流程。
- 新项目用途：将“想要的效果”变成可实现的设计规则与验收；非 UI 项目改写成输入输出或设备交互。
- 注意：来源文档包含部分旧描述（例如联系区已移除但仍有旧段落、删除确认状态前后不一致），应以当前批准方案和代码证据为准。

## TECH_STACK.md

- 定位：技术选型、目录、环境变量、编码约束、运行/构建命令和部署方案。
- 新项目用途：记录选型理由、版本策略、成本/限制和替代方案；不把未经验证的命令当事实。
- OwnerWeb 特例：Vite/React/Three.js/Hono/D1/KV/COS、Worker/Node 双后端、具体密钥名均不通用。

## DATA_MODEL.md

- 定位：实体字段、关系、序列化、接口、校验、权限、迁移和敏感字段边界。
- 新项目用途：即使不是数据库，也记录文件、消息、配置或命令数据模型；完全不适用则明确说明。
- 注意：来源文档存在“线上 COS”与早先“视频外链”历史叙述，以及“当前响应格式尚未统一”与任务已完成的张力；初始化新项目必须分开记录目标与实际并用证据校对。

## ARCHITECTURE.md

- 定位：总体架构、目录职责、页面/路由、请求链路、数据流和边界。
- 新项目用途：区分计划结构和当前实际结构，避免把未来目录写成已有目录。
- OwnerWeb 特例：前端、Worker、D1、KV、COS 和具体路由不可复制。

## TASKS.md

- 定位：可执行的编号任务清单、状态、阶段、依赖和范围约束。
- 新项目用途：每项应有目标、关联需求、验收和验证方式；默认一次一个任务。
- 注意：来源存在编号跳跃、阶段顺序与历史完成项交错，这套历史可保留在 OwnerWeb，但新项目使用稳定编号，并在替代/取消时保留记录。

## PROGRESS.md

- 定位：当前状态与带证据的工作日志。
- 新项目用途：摘要必须最新，历史记录记录实际修改、命令结果、未验证项和阻塞。
- 不应复制：OwnerWeb 的个人经历、日期、部署状态、历史修复。

## LEARNINGS.md

- 定位：项目实证问题的现象、根因、解决和预防。
- 新项目用途：只在调查/修复后记录证据；区分推测、待调查和已证实根因。
- 不应复制：代理限制、SQLite、Workers、Hono、PCB 等特定踩坑。

## DEPLOY.md

- 定位：本地运行、构建、配置、迁移、部署、上线验收、回滚和常见问题。
- 新项目用途：根据交付形态填写；没有云部署时记录实际发布方式，不自动套云服务步骤。

## 统一工作流

1. 读取当前项目入口规则和所有相关记忆。
2. 澄清项目与本期范围。
3. 讨论技术栈、约束和效果。
4. 提交确认稿并等待明确通过。
5. 按模板建立或合并九份文档与协作规则。
6. 校对需求—验收—任务—架构—技术栈的一致性。
7. 一次执行一个任务，验证并同步文档。
8. 以事实、文件和验证结果报告，不虚报完成。
