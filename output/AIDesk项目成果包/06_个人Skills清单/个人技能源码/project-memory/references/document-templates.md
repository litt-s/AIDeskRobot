# 项目记忆文档模板

初始化时将本文中的结构展开为九个独立 Markdown 文件，填入用户批准的信息。标题使用实际项目名称。目录默认 memory_bank/；已有 memory-bank/ 时沿用。每份规格文档在开头注明状态（已确认/待确认）、最后更新日期，区分目标方案与已实现状态。只记录环境变量名及用途，不写真实值。

## PRD.md — 需求与验收

```markdown
# <项目名> 产品需求

## 确认记录
- 确认日期：
- 确认依据：用户明确通过的需求与范围摘要。

## 项目概述与目标
## 目标用户与角色
## 核心使用场景与流程
## 功能范围
| 需求 ID | 功能与行为 | 优先级 | 本期/后续 | 验收 ID |
|---|---|---|---|---|

## 不做项
## 期望效果与交付物
## 非功能要求
性能、可用性、兼容性、隐私等实际适用约束。

## 验收标准
| 验收 ID | 前置条件与操作 | 预期结果 | 验证方式 |
|---|---|---|---|

## 待确认事项
## 范围变更记录
```

验收应可观察，避免“美观”“性能好”等无法验证的空泛描述。目标与现状分别表述。

## TECH_STACK.md — 技术选型与开发规范

```markdown
# <项目名> 技术栈

## 已批准的技术方案
| 层/用途 | 技术及版本策略 | 选择理由 | 限制与替代方案 |
|---|---|---|---|

## 运行环境与工具
## 目录及编码约定
## 依赖与锁文件策略
## 环境变量
| 名称 | 用途 | 作用环境 | 是否敏感 | 配置位置 |
|---|---|---|---|---|

## 开发、构建与验证命令
明确执行目录及前置条件；没有命令时写待建立，不编造。

## 外部服务、预算与平台约束
## 技术决策记录
## 待决问题
```

前端、后端、数据库、存储、认证、测试、部署按项目适用性填写；无相应层时说明原因。

## DESIGN.md — 预期效果与交互

```markdown
# <项目名> 设计与交互

## 设计来源与已确认参考
## 期望完成效果
## 页面/界面/操作入口清单
## 核心流程与交互
## 视觉规范
颜色、字体、间距、组件及布局，均来自已确认设计。

## 状态与反馈
加载、空数据、失败、成功、权限不足及危险操作确认。

## 响应式、兼容性与无障碍
## 设计验收与对应需求
## 未决设计项
```

无图形界面项目改写为 CLI 输入输出、协议交互或设备操作与反馈规则，不虚构页面。

## DATA_MODEL.md — 数据与接口契约

```markdown
# <项目名> 数据模型与接口

## 数据范围与存储位置
## 实体、字段与关系
| 实体 | 字段 | 类型 | 必填/默认 | 约束与含义 |
|---|---|---|---|---|

## 数据生命周期与迁移
## 接口/命令/消息协议清单
| 方法或操作 | 路径/名称 | 输入 | 输出 | 权限 | 错误行为 |
|---|---|---|---|---|---|

## 输入校验与序列化
## 身份与权限
## 敏感字段与公开字段边界
## 示例与边界情况
## 待确认事项
```

无数据库仍可记录内存对象、文件格式、消息或配置模型；完全无数据模型时说明不适用。

## ARCHITECTURE.md — 项目结构与边界

```markdown
# <项目名> 架构与项目结构

## 总体架构
## 计划结构与当前实际结构
标明哪些目录已经存在，哪些待创建。

## 模块职责与依赖方向
## 路由/命令/入口关系
## 请求链路与核心数据流
## 外部集成与系统边界
## 错误处理、权限及配置边界
## 架构决策与变更
```

目录说明记录职责，不仅罗列文件。规划结构与实际结构不能混写。

## TASKS.md — 编号任务清单

```markdown
# <项目名> 开发任务清单

## 批准记录与执行模式
- 已批准范围：
- 确认日期与依据：
- 模式：默认单任务；用户明确授权后可连续执行，但一次只进行一个任务。

## 状态约定
待开始 / 进行中 / 待验证 / 已完成 / 阻塞 / 已取消 / 已替代。
只有验收通过且文档同步后才勾选完成。

## 当前任务
- 当前任务 ID：无（初始化）

## 任务清单
### T-001 <任务标题>
- 状态：待开始
- 关联需求与验收：REQ-001 / AC-001
- 目标：
- 范围与不包含项：
- 前置依赖：
- 交付物：
- 验收条件：
- 验证方式：
- 需同步文档：

## 新发现问题与未批准候选任务
## 取消、替代与任务范围变更记录
```

保留已有项目的编号体系。任务粒度应有明确可验证结果，不能把整项目写成一个任务，也不要给琐碎文件修改各建任务。存在现有完成项时先查证，不凭模板直接勾选。

## PROGRESS.md — 当前进度与证据

```markdown
# <项目名> 当前进度

## 当前摘要
- 当前阶段：
- 当前任务：
- 最近已完成：
- 待验证：
- 阻塞与下一可执行任务：
- 部署状态：未部署/已部署待验收/线上验证通过。

## 本次初始化
- 已完成需求、技术方案和任务拆分确认。
- 已建立项目记忆文档。
- 尚未实现业务功能（适用于新项目）。

## 工作记录
### YYYY-MM-DD — T-001
- 实际完成效果：
- 修改文件：
- 验证命令/步骤与真实结果：
- 未验证项及原因：
- 新问题与阻塞：
- 同步文档：
```

当前摘要保持最新；历史记录保留日期与任务 ID。不要把已失效的历史待办继续留在当前“进行中”。

## LEARNINGS.md — 问题与经验

```markdown

## 已确认的问题
暂无项目实证问题（初始化时）。

## YYYY-MM-DD — <问题标题>（关联 T-xxx）
- 现象及复现条件：
- 根因与证据：
- 解决方法：
- 验证结果：
- 以后注意：

## 待调查问题
将推测与已证实根因区分。
```

只记录本项目真实遇到的问题，不移植来源项目的踩坑历史。

## DEPLOY.md — 运行与交付

```markdown
# <项目名> 运行、部署与交付

## 交付与部署目标
## 环境与权限前提
## 本地初始化与启动
## 构建和产物
## 配置与密钥管理
## 数据迁移、备份与恢复
## 部署步骤
注明执行目录、适用环境和前提；命令经验证后记录验证日期。

## 上线验收清单
## 回滚方案
## 当前部署状态与验证记录
## 常见问题
```

无需云部署时写实际交付方式，例如可执行文件、固件烧录或本地运行。记录计划与实际执行状态；生成文档不构成发布授权。

## 一致性检查

- 每个本期需求都有验收与任务承接，任务不超出需求边界。
- 当前执行项及状态在 TASKS 与 PROGRESS 一致。
- DESIGN 的流程、DATA_MODEL 的契约、ARCHITECTURE 的链路使用同一名称。
- TECH_STACK 与 DEPLOY 的环境、命令和平台约束一致。
- 待确认项没有被当成批准决定，尚未实现功能没有被写成已完成。
- 修改后没有遗留相互冲突的当前规则，历史决策明确标记已替代。
