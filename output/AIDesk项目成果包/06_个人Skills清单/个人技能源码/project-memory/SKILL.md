# 项目需求协商与记忆库开发

将项目从需求沟通推进到技术选型、文档建立、编号任务执行和验收。使用中文沟通，除非用户要求其他语言。把项目记忆保存在项目文件中，使后续会话能够恢复上下文。

## 1. 先了解项目，禁止跳过确认

读取用户调用参数和当前会话中已经明确的信息。先定位目标项目目录，读取现有 AGENTS.md、CLAUDE.md 及项目记忆；只进行必要的只读调查。在需求、技术栈和任务拆分获得明确确认前，不生成业务代码、不安装依赖、不创建项目脚手架、不写入已批准的项目记忆。

每次调用先确认本次要做什么项目、什么工作。新项目完整澄清；已有项目先概括已有目标、技术栈和进度，询问本次目标与变化，仅补问缺失信息，不让用户重新回答已确认的全部需求。

分轮提问，每轮约 3–5 个相关问题，允许用户自由描述。优先询问：

- 项目是什么、解决什么问题、面向谁；是新建还是继续现有项目。
- 核心使用流程、必须实现的功能、优先级和本期明确不做的内容。
- 期望完成的效果、交付物和可观察的验收标准；有界面时询问页面、视觉、交互、终端和参考设计。
- 平台、运行环境、部署地区、预算、时间、现有基础和技术偏好。
- 与项目相关的数据、角色权限、登录、外部服务、性能及隐私约束；只问适用项，不默认所有项目都需要网站、数据库或登录。
- 项目名称、目标目录；新项目记忆目录默认 memory_bank/，已有 memory-bank/ 时沿用，两个目录都存在时先判断现有权威来源，不能静默合并或重复维护。

不要把未知条件自行当成已确认事实。把建议、假设和待确认项分别标明。用户没有回复、工具等待结束、会话中断都不代表通过。当前任务仅为制作本 Skill 时，不执行上述项目启动访谈；这些步骤用于未来调用。

## 2. 商讨技术栈并取得明确通过

依据实际需求给出一个推荐方案；只有存在实质取舍时提供少量备选。解释框架/语言、运行时、数据存储、接口、测试和部署的选择理由、费用、学习成本及局限。对 CLI、桌面、嵌入式或无数据库项目使用相应方案，不套用网页项目结构。

版本、平台能力和价格不确定时查询资料或检查现有依赖，不复制来源项目的版本与免费额度结论。记录无法验证的限制。用户已有确定技术栈时尊重该决定，仅指出与需求直接冲突的部分。

提供“项目确认稿”，包含：

1. 项目名称、目标、用户与核心流程。
2. 本期范围、后续范围和不做项。
3. 期望效果与编号验收标准 AC-001 等。
4. 推荐技术栈、选型理由、环境与部署方式。
5. 编号任务拆分、依赖、优先级、每项验收与验证方式。
6. 项目路径、记忆目录、执行模式、待决问题。

明确询问是否通过需求、技术栈和任务拆分；说明通过后会建立文档并开始第一个可执行任务。按用户反馈修订；影响实现的关键问题未决时继续商讨。已有会话中用户明确批准了同一范围时沿用批准，不反复请求。

## 3. 通过后建立项目记忆

读取 references/document-templates.md，按已批准的项目实际内容生成九份文档，不能只创建空标题。初始化 PRD、TECH_STACK、DESIGN、DATA_MODEL、ARCHITECTURE、TASKS、PROGRESS、LEARNINGS、DEPLOY。不适用的章节写明“不适用”及理由；未决定的非阻塞事项注明负责人、影响和解决时点。

使用同一个已选定记忆目录，统一所有路径。新项目默认 memory_bank/；已有项目使用现有目录。写入前检查文件是否存在，已有文件先全文读取再合并，保留有效内容、任务编号、用户手写内容和历史记录。不要复制 OwnerWeb 的姓名、域名、账号、历史完成项、配色、React/Cloudflare 技术栈或模型代理限制。

参考 assets/AGENTS.template.md，在根 AGENTS.md 中添加项目协作规则。已有 AGENTS.md 时仅合并必要段落，保留原有规则并处理冲突，不整体覆盖。仅使用 Claude Code 且没有 CLAUDE.md 时建立简短 CLAUDE.md，指向 AGENTS.md 和实际记忆目录；已有 CLAUDE.md 时合并引用，确保后续会话能发现规则。

记录用户批准的范围、日期和确认依据；不能编造批准或把规划功能写成已实现。建立文档后校对术语、技术选型、路径、需求编号、任务编号及状态的一致性。

## 4. 按编号任务执行

开始工作前读取全部核心规格：PRD、TECH_STACK、DESIGN、DATA_MODEL、ARCHITECTURE、TASKS，以及 PROGRESS 的当前摘要和相关 LEARNINGS；部署工作还要读取 DEPLOY。大文件可分段阅读全文；同一会话中已读且未变化的内容不重复读取。

选择一个已批准、依赖满足的编号任务，标记进行中，说明本项范围。一次只执行一个编号任务，不同时开始后续任务，不实现清单外功能。完成本项验证和文档同步后，若用户已经授权连续执行，可顺序选择下一个；否则完成一个任务即报告结果并停止。默认单任务模式，将模式写入 TASKS 和 AGENTS。

按 DESIGN 对齐界面与交互，按 DATA_MODEL 对齐字段、协议、鉴权和校验，按 ARCHITECTURE 遵守职责、边界与数据流。实现中发现规格有误时先修正文档；改变已批准范围、验收或技术栈的方案须再次取得明确确认，然后改代码。普通实现细节在已批准边界内自行解决。

发现范围外问题时记录为待处理项，不顺手实现。不能擅自删除 design/、记忆库或用户资源；真实密钥不得进入代码、文档、提交或前端。数据访问通过适合所选技术栈的可信接口和授权边界，不强制所有项目使用云函数或 src/services/。

## 5. 验证并同步文档

每次有意义的实现、依赖、配置、路由、界面、接口、数据、部署或验收变更，结束前同步文档：

| 变化 | 同步文件 |
|---|---|
| 产品范围、目标用户、功能、验收 | PRD.md |
| 技术选型、依赖、工具、命令、环境变量 | TECH_STACK.md |
| 页面、视觉、交互、响应式、用户流程 | DESIGN.md |
| 数据实体、字段、接口、鉴权、校验 | DATA_MODEL.md |
| 目录职责、路由、模块边界、请求链路与数据流 | ARCHITECTURE.md |
| 任务范围、依赖与状态 | TASKS.md |
| 当前状态、完成证据、进行中事项、阻塞和新问题 | PROGRESS.md |
| 已确认的问题现象、根因、解决和预防 | LEARNINGS.md |
| 本地运行、构建、部署、备份、回滚与上线检查 | DEPLOY.md |

执行与当前任务相称的构建、静态检查、测试或手工验收。记录实际命令、结果、失败和未执行的原因。代码写完但验收未通过时标为待验证，不勾选完成；本地通过不等于已部署，部署成功不等于线上业务已验证。

维护 PROGRESS 的当前摘要，将历史记录按日期与任务 ID 追加；被新方案替代的决策注明替代关系，避免旧的“待部署”和新的“已上线”同时作为当前状态。TASKS 与 PROGRESS 的状态必须一致。

当工作是完善文档时，全文读取目标文档，优先补齐 TODO，同时修正与当前批准范围或事实冲突的非 TODO 内容，保留有效通用规则。报告补全内容和实质修改理由。

纯文本代理环境中遵守本项目已确认的通信限制，不调用会注入图片的浏览器工具；普通环境不自动继承 OwnerWeb 的代理禁令。

## 6. 结束与恢复

回复说明当前完成的任务 ID、实现效果、修改文件、验证证据、尚未完成或阻塞的内容，以及已同步的文档。不要宣称未执行的检查已通过。

下一会话以项目文档恢复：确认目标项目和本次任务，读取协作规则、当前进度和任务依赖，对照代码验证容易过时的事实。冲突时记录实际证据并修正文档，产品意图有歧义时向用户确认。
