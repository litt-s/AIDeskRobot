- Cloudflare 能力核实（2026-10-14，据官方文档原文）：**Workers 支持主动向外部服务器发起 WebSocket**——`new WebSocket(url)` 可用，也可用 `fetch()` 带 `Upgrade: websocket` 头（后者可 `accept({ allowHalfOpen: true })` 做半开）。我此前判断"Worker 不能主动发起 WebSocket"是**错的**。需要与之区分的是另一件事："把一条 HTTP 请求的消息推给已建立的入站连接"仍然需要 Durable Objects，两者不是一回事。Durable Objects 在 Workers 免费版可用但**仅限 SQLite 后端**（10 万请求/天、5 GB 存储），付费版 $5/月起含 100 万请求。
- 该核实的直接结论：实时语音链路**可以留在 Cloudflare**，不必为此购买国内服务器或做 Node 迁移。上游语音服务的连接都是几秒级短连接（每轮识别、每段合成各一次），落在 Workers 支持范围内；机器人侧更可只用 HTTP（上传整段音频 + 流式读回音频），固件无需引入 WebSocket。

- 火山语音实测配方（2026-10-14，烟测通过）：**ASR 声明必须与数据一致**——发送剥头裸 PCM 时必须声明 `audio.format="pcm"`、`codec="raw"`、`rate=16000`、`bits=16`、`channel=1`；按官方示例声明 `format="wav"` 会返回 `The audio could not be decoded using the declared format`。ASR 端点 `wss://openspeech.bytedance.com/api/v3/plan/sauc/bigmodel_async`，200 ms 一帧，最后一帧序号取负并置 `NEG_WITH_SEQUENCE`。
- TTS 三种输出格式实测：请求 `pcm` 返回**裸 PCM**（无容器头，16 kHz 单声道 16 位，机器人可用 `robot_audio_play_pcm()` 直接流式播放）；请求 `wav` 返回带 RIFF 头的 WAV（注意其 size 字段为 0xffffffff 的流式头）；请求 `mp3` 返回 ID3 容器。端点 `https://openspeech.bytedance.com/api/v3/plan/tts/unidirectional`，响应为 `text/plain` 下的行分隔 JSON，音频在 `data` 字段（base64），以 `code=20000000` 结束。
- 火山账号调用语音接口前**必须先在控制台开启 Agent Plan 抵扣**，否则一律 `403 Forbidden.AgentPlanDeductNotEnabled`；这与代码无关，排查前先看设置。

- Workers 主动建 WebSocket 时的 URL 协议（2026-10-14 实测）：用 `fetch()` + `Upgrade: websocket` 头建连时，URL **必须写 `https://`，不能写 `wss://`**。写 `wss://` 会立刻被 Fetch API 拒绝，错误原文 `Fetch API cannot load: wss://openspeech.bytedance.com/...`。`wss://` 只有 `new WebSocket()` 构造函数接受，而构造函数无法自定义请求头，火山需要 `X-Api-Key` 等头，所以两者不能混用——走 fetch + Upgrade 是同时满足"自定义头"和"发起连接"的唯一组合。
- 同一次排查中我一度判断"本地 `wrangler dev` 不支持出站 WebSocket"，**这个结论是错的**，真相是 wrangler dev 进程在重载时卡死了：请求一直排队、日志停在 `Reloading local server...`。改成 `https://` 并**重启 dev server** 后，同一条请求 611 ms 返回 `HTTP 401`（占位密钥），证明握手确实到达了火山。教训：把"请求挂住"归因于运行时不支持之前，先确认 dev server 本身还活着（看是否有新日志、重启一次再试），否则容易得出完全相反的结论并据此改架构。
- 火山 ASR 的建连阶段必须有独立超时：`transcribe()` 原实现的 20 秒计时器挂在拿到 socket **之后**，握手阶段卡住时计时器根本还没开始。已给那次 `fetch` 加 `AbortSignal.timeout`。
- 但 `AbortSignal` 并非万能：实测握手挂起时超时信号打不断那次 fetch。因此 `server/voice/pipeline.ts` 另加 `withDeadline()` 做墙钟竞速，给识别/合成/模型三步各设上限，宁可放掉后台那次请求，也要保证机器人拿到一个明确的失败帧而不是无限等待。
- 又一次裸 `INSERT INTO ... VALUES (?...)` 踩坑：0005 给 devices 加了两列后，`POST /api/devices` 的 11 个占位符对不上 13 列，测试立刻报 `table devices has 13 columns but 11 values were supplied`。这是该项目第二次出现同类问题（前一次是 device_commands 的 9 对 10）。**新增表或改表时，INSERT 一律显式列出列名**，让迁移加列不会静默错位。

- `robot_audio` 的麦克风 consumer **只有一个槽位**，且唤醒词引擎已经占用它（`robot_audio_register_pcm_consumer` 是覆盖语义）。云端语音录音若直接调它，会把唤醒词悄悄顶掉——这种故障不会报错，只会表现为"唤醒词突然不灵了"。为此新增 `robot_audio_add_pcm_tap`／`remove_pcm_tap`，在既有 consumer 之后追加最多 2 个旁路；主 consumer 的调用位置和顺序完全不变。旁路回调运行在采集任务里，只允许拷贝样本和更新计数器，任何阻塞操作都会丢帧。
- 唤醒提示音与录音的先后（2026-10-14 编码时的取舍）：唤醒路径先 `robot_audio_set_capture_paused(true)` 再放提示音，所以云端录音**必须**等提示音播完（轮询 `robot_audio_is_playing()`，上限 2.5 s）再解除暂停，否则每一句话的前面都会粘上提示音，识别结果里会多出一段噪声开头。
- 云端一轮的两个状态通知（开始/结束）必须成对发出，**包含提前返回的所有分支**：robot_app 在收到触发请求时就切到 `CLOUD_VOICE_ACTIVE`，若某条失败路径只 return 而不通知结束，机器人会永久卡在这个状态，表现为麦克风不再响应。因此把"通知开始 → 执行 → 通知结束"包成一个外层函数，内层只管干活。
- 固件改动可以在本机做编译校验，不必等一整轮 `idf.py build`：`build/compile_commands.json` 里存着 CMake 生成的完整编译命令，取出目标文件那一条、把 `-o` 改到临时文件（同时改 `-MF`），用同一个交叉编译器重跑即可，报错与真实构建一致。三个坑：①**不要用 `-fsyntax-only`**——`-Wformat-truncation` 这类警告来自中端优化阶段，只在真正编译时才报，`-fsyntax-only` 会漏掉（本轮就是这样漏掉了 `robot_voice.c` 的一处真实截断）；②Windows 命令行长度上限会让 `main/robot_app.cpp` 那条（约 8 KB）报"命令行太长"，把参数写进 `@response` 文件传即可绕过；③`-Wall -Werror=all` 在真实构建里是生效的，所以警告会当错误。改 `robot_app.h` 这类被多处包含的头时，要连同所有包含它的源文件一起校验（本工程里是 `robot_app.cpp` 与 `app_main.cpp`）。校验脚本与临时产物用完即删，不要留在 build 目录里。
- 上面这个校验脚本还有一个更阴的坑（2026-10-14 撞到）：CMake 会把带字面引号的宏写成 `-DMBEDTLS_CONFIG_FILE=\"mbedtls/esp_config.h\"`，而这**恰好**把"按 `"` 切分命令行"的朴素分词正则打断——宏定义被撕成两半，传进编译器时变成空值，于是 `#include MBEDTLS_CONFIG_FILE` 展开成非法的 `#include`，被测文件瞬间报出十几条 mbedtls 错误。修法是分词前把 `\"` 换成哨兵、写响应文件时再还原（响应文件里 `\"` 会被 GCC 还原成字面引号，正是这条定义需要的）。**判别"是工具坏了还是代码坏了"的依据是因果关系**：报错发生在 `esp_crt_bundle.h`／`mbedtls/build_info.h`，而我这次只加了一个 typedef 和一个函数声明——两者之间没有因果。更硬的证据是：**未被我改动的 `robot_music.c` 也含同一条定义**，而它同样失败。写完校验工具后，先拿一个"明知应该通过"的文件跑一遍，能省掉整轮误判。
- 开发来源校验从"逐个登记 IP"改为"按地址类型判断"（2026-10-14，用户实测反馈）：用户一直在用局域网地址访问控制台，而电脑的局域网地址每次换网络都变（10.34.20.209 → 10.243.104.162 → 192.168.137.1 热点网关），`.dev.vars` 里登记的那一个一旦过期就报"请求来源不受信任"，且报错发生在**登录之前**，看起来像登录坏了。现在 development 下放行 host 为 loopback 或私有地址字面量（10/8、172.16/12、192.168/16、169.254/16）的 origin，不必再逐个登记。
- 这个放宽为什么是安全的：公网页面无法把私有地址作为自己的 origin；DNS 重绑定也不行，因为 Origin 头带的是页面**加载时所用的名字**，而不是该名字解析到的地址。攻击者必须先控制用户内网里某个地址上的内容。另外 cookie 是 `sameSite: Lax`，跨站 POST 本来就不带凭证。production 在到达这段逻辑前就已返回，只接受同源，因此部署实例完全不受影响。`DEV_ALLOWED_ORIGINS` 保留给隧道域名等覆盖不到的情况。
- 随之必须改的是那条锁定旧规则的测试（原 `tests/trust.test.ts` 断言 10.34.20.210 在只登记了 .209 时必须为 false）。放宽一条安全规则时，要把"现在放宽到什么程度、哪些形状仍然必须拒绝"一起写进测试——本轮补了 10 条反例：11/8、193.168、172.32、`127.0.0.1.evil.org`、带路径/用户信息/查询的 origin、非 http(s) 协议、以及 >255 的八位组。
- `snprintf` 往一个定长缓冲写"不定长输入"时，`-Werror=format-truncation` 会精确算出最坏长度并报错（例如把 256 字节的响应体拼进 160 字节的 `last_result`，报"output between 23 and 291 bytes into a destination of size 160"）。凡是把外部数据（HTTP 响应体、上游错误消息）拼进固定缓冲的地方，都要用 `%.Ns` 限定宽度，而不是指望 `snprintf` 自己截断。

- 真机语音链路排查（2026-10-14，结论：**仍未定位**，但用证据排除了整类假设）。现象：`listen` 指令两次回报"已开始收音"，服务器也确实建了设备对话，但该对话**零消息**，且整轮耗时约 40 秒（10 秒录音 + 25 秒识别超时上限）。据此判定**卡在火山识别那一步**。
  已本地实测排除的假设（每一条都单独跑过探针，而不是推理）：
  ① "本地 workerd 不支持出站 WebSocket"——用一个本地回声服务 + 临时 Worker 验证，`fetch` + `Upgrade` 得到 `status=101`，双向收发 `echo:hello`/`echo:ping` 全部正常。
  ② "经 TLS 连远程 WebSocket 不行"——对两个公网 WSS 服务（postman-echo、echo.websocket.org）同样得到 101 并成功回显。
  ③ "`new Blob([subarray])` 忽略 byteOffset，导致每帧都带上整段录音"——实测 `blobHonoursOffset: true`、gzip 往返 `roundTripOk: true`。
  ④ "采样率/格式声明与采集不一致"——固件 `robot_audio_init` 强制 `sample_rate_hz == 16000`，采集为 16 kHz 单声道，与请求里声明的完全一致。
  排查方法本身值得保留：**把"运行时能不能做这件事"和"我们的代码有没有做对"分开验证**，前者用最小探针（一个回声服务 + 一个只做这件事的 Worker）单独确认，否则只会在整条链路上反复猜。探针用完即删，不要留在工程目录里。
- 同一轮里我发现并修掉的两处**真实缺陷**（与上面的现象未必同因，但都是真问题）：
  ① `transcribe()` 里 `AbortSignal.timeout(20000)` 挂在 `fetch` 上，握手成功后**信号仍然armed**——升级后的连接会被它按 20 秒砍断。已改为 `AbortController` + 在拿到 socket 后立刻 `clearTimeout`，让建连超时只管建连。这个 bug 平时看不见（识别通常 1–2 秒完成），只有在慢的时候才变成"莫名其妙断线"。
  ② 识别请求漏了 `enable_ddc: true`，而跑通的烟测里是有的。既然那条配置验证过，就不该留无谓差异；已补齐并加注释说明不得随意删改。
- 另一个独立问题：`speak` 走的是 `CloudSpeak` → AIUI 会话，而用户的固件是**无 AIUI 模式**，所以它永远回报"设备未配置语音服务"。已改为优先走 `/api/device/say`（云合成，不需要会话），失败才回落内置语音栈；同时 `robot_voice_say()` 与语音一轮共用同一段分帧读取与播放代码（抽出 `voice_open_request` / `voice_read_response`），避免两处各写一份解析。

- 无 AIUI 模式（`ROBOT_ALLOW_VOICELESS`）会**提前 `return`**：`SetupOnlineServices()` 在凭据缺失时于 AIUI 段就返回，后面的唤醒词（`robot_wakeup_init`）与手势初始化全被跳过。**因此这类固件的唤醒词引擎从未运行，麦克风也从未被任何东西真正使用过**——采集本身（`robot_audio_start`）在更早的 init 阶段就完成了，所以"麦克风有没有在工作"这件事既没人验证也不会报错。排查无 AIUI 配置的语音问题时要记住这一点。
- 麦克风电平日志原先只在 `SESSION_ACTIVE` 分支里打印，于是**恰恰在最需要它的配置（无 AIUI）中一次都不会出现**。已改为任何状态下都打印、约每秒一行、静音时显式标注 `(silent)`。这类"诊断代码只覆盖了正常路径"的问题很隐蔽：日志本身没写错，但它永远不会在你需要的时候出现。
- 判断"录音是否真的录到东西"时，**不要只看"有没有上传"**：固件只要求录音超过 100 ms 就会上传。真正有信息量的是①录音是否跑满时长上限（跑满说明能量 VAD 全程没检出说话）②服务端量出来的峰值/有声占比。本轮三次失败都是 11–12 秒 ≈ 跑满 10 秒上限 + 2 秒识别，于是"识别为空"和"VAD 不触发"被同一条证据串起来：**两个独立检测器都认为音频里没有人声**。
- 区分"麦克风完全没采到"与"采到了但没听到说话人"需要的是**电平数字**，不是错误码——这两种情况从外部看一模一样（都是"没有听清"），修法却相反。因此把 `describeAudio()` 的结果直接写进用户能看到的失败原因里，而不是只写进日志。

- 麦克风引脚与声道（2026-10-14，据原理图 U4 与固件双向核对）：U4 是 6 脚 I2S MEMS 麦克风，**SCK=GPIO5、WS=GPIO4、SD=GPIO6**，VDD=3.3V、GND，第 6 脚为 **L/R 声道选择**。固件三个引脚与原理图完全一致，采样 16 kHz/16 位/单声道。
- **L/R 脚（第 6 脚）在原理图的 PDF 文字层里没有网络标号**（其余各脚都有），连线是矢量图形，文字提取看不到。而这一脚决定麦克风把数据放在左声道还是右声道：接 GND → 左，接 VDD → 右。固件读的是**左**声道（`I2S_STD_SLOT_LEFT`）。**读错半边不会报错，只会全是静音**——这与"录音 10 秒、有上传、但识别说没有人声"的现象完全吻合，是当前最值得先量的一处（万用表量第 6 脚对地是否导通即可）。已把这一项做成 `ROBOT_MIC_RIGHT_CHANNEL`（默认 n），排查时不必改代码。
- 读原理图 PDF 的一个实用做法：用 pypdf 带坐标提取文字（`extract_text(visitor_text=...)` 拿 `tm[4]/tm[5]`），再按"离目标文字最近的元素"列出邻域，比直接 dump 全文可靠得多——全文顺序会把连线关系打乱。但要注意**它看不到矢量连线**，所以像 L/R 这种没有标注的脚，最终仍需万用表确认。
- 用户一句"**之前的源码麦克风是好使的**"直接推翻了整条硬件怀疑线（麦克风本体、供电、引脚、声道接法）。教训：**在开始怀疑硬件之前，先确认同一块板子上有没有能用的参照实现**。本工程网盘里就有同板型的完整板级源码（`xiaozhi-deskemoji-gesture-music-taibai-main/main/boards/esp32-s3n16r8-emoji`），把它拿来逐项对比 I2S 配置，比对着原理图和现象猜快得多，也有结论得多。对比结果：声道/位宽/移位/端口**全部一致**（我先前怀疑的 L/R 声道问题因此被证伪），真正的差异只有**采样率 24000 vs 16000** 和 DMA `frame_num` 240 vs 640。
- 改采样率时最容易漏的是**散落在各处的"每毫秒多少采样"硬编码**：`robot_audio.c` 的 I2S 时钟、`robot_voice.c` 的静音判定与录音时长（`sample_count / 16`、`recorded_samples / 16`）、以及服务端算音频秒数的地方。只改 I2S 而不改这些，采样率一动静音判定和时长统计就全错，而且**不会报错**。另一个必须同步的点：固件得把自己实际的采集率告诉服务端（`X-Sample-Rate` 头），否则两边各自维护一个率必然漂移。注意采集率与回放率是**两件事**——回放要跟着服务端合成的采样率走，本工程里它固定 16 kHz，不该跟着采集一起变。
- **`峰值` + `均方根` 不足以区分两类完全相反的问题**（2026-10-14 实测教训）。实测拿到 `峰值 32768 / 均方根 18252 / 有声占比 99%`，这个组合同时符合两种假设：①真实语音被放大 16 倍（+24 dB）后削顶；②数据根本不是语音，而是满量程噪声（均匀分布于 int16 全域的理论均方根是 `65536/√12 = 18919`，与实测只差 4%；`|x|>300` 的概率是 99.1%，正是"有声占比 99%"）。两者修法相反，靠这两个数分不出来。**能分开的是另外两个统计量，而且都很便宜**：
  - **削顶比**（样本落在 ±满量程的比例）：放大过头会让大量样本被 clamp 到轨上；噪声只会偶尔碰到轨。
  - **过零率**（相邻样本变号的比例）：即便削顶，语音仍有波形相关性，远低于 20%；噪声互不相关，稳定在 50% 上下。**这一条尤其好用，因为它不依赖任何幅度假设。**
  教训是通用的：当"现象都长一样、修法却相反"时，先问**哪个观测量能把它们分开**，再把那个量加进诊断输出，而不是靠现有数字推理。另外把诊断数放进**用户能看到的地方**（这里写在失败原因里、落库到设备对话）比放日志里更值——上一轮就是因为失败完全静默而白白多花了几轮排查。
- 上面这两条补上后**一次就定案了**（2026-10-14，第二轮实测）：读数是 `峰值 32768 / 均方根 18552 / 有声占比 99% / 削顶 16% / 过零 1%`。
  - `过零 1%`（而非 50%）**直接排除噪声**——噪声相邻采样互不相关，过零必然约一半；1% 说明是高度周期性的低频波形。
  - `过零 1%` 同时**排除纯正弦／工频干扰**：正弦的均方根/峰值比恒为 0.707 且**根本不会削顶**，而实测是 0.566 且削顶 16%。这一步很关键——单看"低频、幅度大、识别不出来"很容易误判成电源干扰去查硬件。
  - 剩下的假设可以做**定量检验**而不只是"说得通"：设语音近似拉普拉斯分布（比高斯更贴近语音），放大 16 倍后削顶，用削顶比例 16% 反解尺度参数，得到理论均方根 **18690**，实测 18552，**只差 0.7%**。反推原始语音均方根约 1580，是正常说话电平。至此判定为"真实语音被放大 16 倍"。
  - 结论与**独立的位对齐推理**一致：24 位麦克风的数据放在 32 位槽高位时，`>> 16` 正好把麦克风满量程映射到 int16 满量程，`>> 12` 恰好放大 16 倍。**测量与原理两条独立路径给出同一个答案，这种一致才是可以改默认值的依据**；只有其中一条时不该改。
- **"定性说得通"和"定量对得上"是两回事**：本轮两次都差点停在"这个假设能解释现象"就动手。真正定案靠的是把观测值代进模型算出理论值再比对（18690 vs 18552）。诊断量已经拿到时，多花一步做数值检验，比再跑一轮实验便宜得多。
- 又一个**"参考实现能用"不等于"参考实现的配置对"**的例子：本工程板级源码的 `>> 12` 与当前固件逐字相同，但它把麦克风送进**带 AGC 的 AFE 前端**（AEC／降噪／VAD），AGC 会把过驱的电平拉回来、唤醒词对中等削顶也宽容，所以它"能用"。我们的云端通道**直接上传原始 PCM**，没有任何前端处理，同样的过驱就是致命的。**比较两份实现的配置时，必须同时比较数据前后有没有别的处理环节**，否则会把"被下游补救过的错误配置"当成正确配置照抄。

- **"烟测验证过"验证的是烟测脚本，不是生产代码**（2026-10-14，本轮最值钱的一条）。烟测脚本与生产代码是**两份独立实现**：前者用 Node 的 `ws` 库，后者走 Workers 的 `fetch` + `Upgrade`。我把两者的帧编码与帧解析逐字节比对过，**确实完全一致**——但两边**传输层给消息的方式**根本不同：`ws` 直接给 `Buffer`，而 Workers 的 `event.data` 类型**由运行时决定**。这个差异烟测永远碰不到，而它正是故障所在。教训：把协议校验通过当成"这条链路通了"是危险的，**只要发送或接收的通道不同，"协议一致"就不蕴含"路径可用"**；验证时必须走生产代码那条通道，或者至少对着两份实现的**边界**（这里是"消息以什么类型进来"）单独确认。
- **未处理的消息类型会静默变成"没有内容"，而"没有内容"长得跟"识别说没听到人说话"一模一样**。原实现只认 `ArrayBuffer` 和字符串，其余一律 `new TextEncoder().encode(... : '')` → 空数组。空数组解析出来是"零长度 payload 的帧"：不报错、`isLast` 为假、错误码为 0，于是流程一直等到 socket 关闭、拿到空文本、上报"没有听清"。**这类缺陷完全没有声音**，而且它会污染整个排查方向——我为此去调了麦克风增益（那确实是另一个真问题，但修完症状丝毫不变）。修法是双管齐下：①`messageBytes()` 把 `ArrayBuffer`／`ArrayBufferView`／字符串／`Blob`／未知形态全部显式处理；②**统计真正收到的响应帧数，一帧都没收到就抛错**（「没有收到任何结果帧」），而不是把"自己没读懂"伪装成"对方没说话"。**这两件事修法完全相反，混为一谈就等于把排查引向错误的一侧。**
- 取 `ArrayBufferView` 的字节要按 `byteOffset` / `byteLength` 取，**不能直接用 `.buffer`**（会连带视图前后的其他数据，帧头直接错位）。这条单独立了一个测试用例钉死。
- 排查到"每一轮都以完全相同的方式失败、且与输入质量无关"时，应当**优先怀疑读取侧而不是被读取的数据**：数据质量问题通常会随输入变化而变化，而"永远同一个结果"更像是一个恒定成立的代码路径。本轮音频从削顶 16% 修到削顶 0%，识别结果一个字都没变——这个"完全没变"本身就是最强的线索，我意识到得太晚了。
- 上面那条**已由真机验证确认**（2026-10-14 当日）：改完 `messageBytes()` + 帧计数后，连续三轮对话全部识别成功并正常回复。可以确定 **Workers 主动发起的 WebSocket 交给 `event.data` 的就是 Blob**（即按规范默认的 `binaryType = "blob"`），而 `ws` 库在 Node 里给的是 `Buffer`——**同一个协议在两套运行时下的交付形态不同，这正是"烟测通过"骗过我们的地方**。此后凡是在 Worker 里收 WebSocket 二进制消息，第一件事就是设 `binaryType = 'arraybuffer'` 或显式处理 Blob。
- 统计音频电平时注意 `abs()` 的边界：`abs(-32768) == 32768`，所以"触顶"要在**两端**都判（`|x| >= 32767`），只判正半边会漏掉一半削顶样本。
- 又一次证明**"同板型的可用参照实现"比对着原理图和现象猜快得多**：本轮先查参考固件的 `>> 12`（发现一致，保住了一条错误方向上的改动），再从 IDF 头文件展开宏，确认 `I2S_STD_PHILIPS_SLOT_DEFAULT_CONFIG` 在 S3 上展开后与参考固件逐字段相同（`slot_mask` 除外，且那一项本项目另外覆盖了）。**读宏的真实展开，而不是读宏的名字**——`PHILIPS_SLOT_DEFAULT_CONFIG` 这个名字掩盖了 `slot_mask=BOTH` 这个默认值。
- 查 IDF 宏展开时，`build/compile_commands.json` 里的 `-I` 路径直接给出了 IDF 安装位置（`/esp/v5.5.5/esp-idf/components/esp_driver_i2s/include`），不必去猜 `C:\Espressif` 之类的默认目录；`i2s_std.h` 按 `CONFIG_IDF_TARGET_*` 分了好几套同名宏，**必须确认目标芯片走的是哪个分支**（S3 走 `#else`）。

## 一个表单就是一次隐式耦合：留空字段的语义必须与"用户想改什么"对齐（2026-10-14 配网页）
- 现象：用户想只改设备码，结果 Wi-Fi 掉了；想只改 Wi-Fi，又担心碰到设备码。
- 根因不在某一行写错，而在**表单的结构**：配网页原先把 Wi-Fi、AIUI 凭据、设备通道挤在同一个 `<form>` 里，且 Wi-Fi 名必填。于是"改设备码"这件事在协议层就必然携带 Wi-Fi 字段（逼用户重选网络），而**密码框留空会被当作"开放网络"写进 NVS**，把已保存的密码覆盖成空 → 连不上 → 退回配网。用户看到的因果是"改了设备码，Wi-Fi 坏了"，真实因果是"提交了半个 Wi-Fi 表单"。**两个功能的耦合常常不是代码耦合，而是"它们共享一次提交"**。
- 规则：**一个表单只表达一个意图**（这里是隐藏字段 `section` + 一个提交按钮）；服务端按显式 section 分派、只写对应的存储命名空间（**这一版分派当天即被下面的修订取代**）；**未提交的字段一律不写**，而不是"空字符串就是空值"。同时把"留空＝不修改"写进页面提示，否则用户不敢留空。
- 同类陷阱：`nvs_set_str(..., "")` 是合法写入，所以设备侧"空"没有天然的"不修改"含义，只有代码显式区分"字段不存在"与"字段为空"才安全。另外，**section 缺失时直接拒绝比猜测字段意图安全**——猜测正是耦合的来源。（该分派已按用户反馈移除，但"拒绝语义含糊的请求"这条仍然成立。）
- 顺带一条产品判断：保存成功的提示应该说明"这次改了哪一段、没动哪一段"（如"设备正在重启；Wi-Fi 与 AIUI 凭据未改动"）。用户对"互相不影响"的信任来自这几句明确的话，而不是来自我们心里的设计。

- **当天随后的修订（2026-10-14，按用户反馈）**：用户要求"配网页不要每段一个按钮，就一个按钮：填了就保存、没填就保持原值"。据此把表单改回**单表单、一个保存按钮**，去掉 `section` 与分派——独立性照样成立。这说明**耦合的根因不是"按钮数量"，而是"必填项 + 空值即覆盖"**：原页面之所以改 A 必伤 B，是因为 Wi-Fi 名必填、密码留空会被写成空串；只要**没有任何必填项、且留空＝不修改**，单表单也能让两个功能互不影响，而且用户操作更少。所以正确表述是"**没有必填项＋留空＝不修改是解耦的充分条件，表单拆不拆只是外观选择**"；前一条把"一个表单只表达一个意图"写成了原则，是把实现选择当成了原则，在此更正。
## 用 PowerShell 脚本改文件时：函数里不要用 Write-Output 做日志（2026-10-14）
- 做法：写一个返回字符串的 PowerShell 函数，把大段新代码替换进现有文件。函数里除 `return` 外还写了 `Write-Output "正在替换 X 字符"` → 这些字符串**一并进入输出流**，被 `$text = Splice ...` 收进变量，最终把日志拼到了文件开头（正文本身正确，但文件首行变成日志）。
- 教训：**在"返回字符串"的函数里用 `[Console]::WriteLine` 记录，不要用 `Write-Output`**；或者把日志挪到函数外。更稳的做法是"先把新代码写成临时文件，再用一次替换拼接"，每一步都能单独核对。
- 附带一条：PowerShell here-string `@' ... '@` 写文件时必须显式指定 UTF-8 无 BOM（`New-Object System.Text.UTF8Encoding($false)`），否则中文与 `••••` 这类字符会被写成 ANSI 或带 BOM；C 源码混入 BOM 会直接编译失败。
- 还有一条通用做法值得保留：**改了 C 文件就一定要真编译**。本轮的验证路径是——从 `build/compile_commands.json` 取出该文件记录的真实编译命令，把 `\"` 转义还原后交给项目自带的 `xtensa-esp32s3-elf-gcc`（`idf.py` 不在 PATH，也烧不了真机，但单文件编译足以证明语法与头文件依赖没问题），再在对象文件里检索新增字符串确认这次编译确实包含新代码。（**2026-10-14 晚更正**：这套"自己分词再把 `\"` 还原"的做法对 `-DXXX=\"...\"` 之类的宏定义会二次转义，只在被测文件不包含 mbedtls 头文件时才碰巧成立；稳妥做法见"配置值的规范化"一节的工具链补记——把原始命令写进 .bat 用 `cmd /c` 执行。）
- **同一类坑再犯一次（2026-10-14 晚）**：这次不是 `Write-Output`，而是**here-string 少了结束标记**——`Swap ... @'` 开的字符串没有以独占一行的 `'@` 收尾，PowerShell 就把**后面整段脚本**当成了字符串内容，于是 DEPLOY.md 被写进一段脚本文本、原本的句子还被截断。修法是按锚点把被污染的区间整段替换回正确内容。两条教训：①**拼接大段文本前，先把新内容写进临时文件并核对长度与首尾行，再做替换**（本次 LEARNINGS 的补充就是这么做的）；②**写完立刻做"关键片段计数"验证**——只可能来自脚本的字符串（`$learn=`、`DEPLOY-add` 之类）必须为 0，别等下一步才发现。
- 顺带一条与"验证"有关的原则：**同一份文件被机器与人工同时改动时，"看起来正常"不是证据**。本次污染把脚本文本和中文正文混在一起，单纯扫一眼很像正常的 Markdown；只有按标题清单（`^#{1,3} `）与关键片段计数逐项核对，才确认了已修好。

## 由用户手动进入的模式，必须有用户手动退出的路（2026-10-14 BOOT 长按进配网）
- 背景：给"已联网"的机器人加一个"长按进配网"的入口时，顺带发现原来的入口本身是个陷阱——配网页**只会写配置**，没有任何"返回"。以前只有"连不上 Wi-Fi 会自动进配网"，那种情况下用户本来就想配网；但一旦允许**用户主动**进入，就必须同时回答"我不想改了，怎么出去"。否则要么手动断电，要么等下一次重启。
- 做法：同一个手势在不同状态下承担对称的语义——不在配网时长按＝进入配网，已在配网时长按＝`esp_restart()`（用已存配置重新联网）。重启比"返回主界面"简单得多，也天然把 Wi-Fi/AIUI/播放栈拉回干净状态；代价是配网中途重启会丢掉"页面里刚填但还没提交的内容"，这可以接受。
- 通用规则：**引入一个新的"模式"时，先把进入与退出成对设计**；退出用重启实现时，要在文档里写清"重启＝用已存配置恢复"，否则用户会担心重启是不是把配置弄丢了。
- 另一条按键经验：改按键语义前先读 `poll_button` 的实现——本项目里长按触发时会把 `long_press_sent` 置位，**释放时不再补发短按**，因此"短按＝唤醒、长按＝配网"可以共存而不会互相触发；如果实现是"长按也发短按"，这个改动就会同时唤醒机器人。
- 还有一个边界要在文档里认下来：进入配网会 `esp_wifi_stop()`，而 `robot_network` 会先把状态置为 `CONNECTION_PROVISIONING`，所以 STA 掉线**不会**再触发 `ROBOT_NETWORK_DISCONNECTED` 事件、也不会自动重连；`time_ready` 被置 false 后，唤醒事件（`WAKE_TRIGGER` 要求 `OFFLINE_WAKE_READY && time_ready`）自然被忽略，因此配网期间说唤醒词不会有动作。这是有意的，不是遗漏。
## "什么都没发生"必须能被日志拆成三层（2026-10-14 BOOT 长按进配网）
- 用户反馈"长按按钮不进入配网了"。这类症状最要命的地方是它把三种完全不同的故障压成同一句话：①手势没被识别（阈值/去抖/按键任务没在跑）；②识别了但事件没被处理（队列/状态分支）；③处理了但网络或界面没起来（Wi-Fi 模式切换失败、httpd 起不来、屏幕被更晚的事件覆盖）。
- 处理方式：**在每一层各留一条日志**——`BOOT long press detected`（按键任务）→ `provisioning requested from BOOT long press`（worker 处理）→ `provisioning: SSID=… URL=192.168.4.1`（网络侧真正起来）。三条日志把"什么都没发生"变成可以二分的三段，不必靠猜。
- 同时改掉了一个我自己设计出来的坑：**同一个手势承担"进入"和"退出"两种语义**。原来的"配网中再长按＝重启"，在 app 状态与网络状态脱节时会表现成"长按没反应"或"莫名重启"。现在手势只有一个含义（打开配网页），"已经在配网页里"也被当作有效结果（重新播提示、重新显示屏幕）——**幂等且可反馈**比"省一次断电"重要。
- 更一般的规则：不要在"用户能看到的状态"和"代码内部的状态"之间留出可能不一致的缝。一旦有缝，用户按按键时看到的行为就取决于缝的哪一侧，而用户无从知道是哪一侧。修法要么让状态只有一个权威来源，要么让动作幂等并回显（本轮选了后者，改动最小）。
## "点按也能进配网"不是按键问题，而是"设备没连上"的告警（2026-10-14）
- 现象：先反馈"长按不进入配网"，紧接着反馈"现在变成了点按进入配网模式"。
- 读代码可以确定这是同一件事的两面：`robot_network_request_reprovision()` **只在 `CONNECTION_CONNECTING` 状态被接受**，所以"短按能进配网"等价于"按下那一刻设备并不在网"。短按分支本次一个字未改——**不是动作被改坏了，而是触发条件一直成立**。
- 顺着这条线索能找出遗留故障：最早的 bug 是"改设备码时把 Wi-Fi 密码覆盖成空"，那 NVS 里存的就一直是空密码 → 永远连不上 → 开机 60 秒内点按＝进配网、超时＝自动进配网；而上一版把"配网中长按"做成重启，于是用户看到的就是"长按没反应"。**三条现象指向同一个状态，而不是三个 bug。**
- 教训一：**当某个动作"行为变了"时，先问它的触发条件是什么**，别先怀疑动作本身。短按的触发条件是"正在连接"，它变得很容易触发就说明连接状态在变差。
- 教训二：**把不可见的状态显示出来**。NVS 里的密码是空串这件事，页面原来完全不显示，于是"我明明填过密码"和"设备连不上"可以长期共存。现在状态卡显示 `（已保存密码）`／`（未保存密码）`，把最有价值的诊断信息放到用户唯一看得见的界面上。**"用户看不见的状态"是排查成本最高的部分，能给用户看就别留在串口里。**
- 教训三：**单表单 + 单一保存按钮**虽然"填了就存、留空就不动"，但它把"误点 Wi-Fi 列表里的网络行"也纳入了同一次提交。因此单表单方案必须配一条前端提醒（选中加密网络却没填密码时拦一次），并明确告诉用户"只改设备码就别碰 Wi-Fi 那一段"。
## 裸 host 没有 scheme：一个"看着在线却永远连不上"的配置陷阱（2026-10-14）
- 真机日志：`E (38077) HTTP_CLIENT: Error parse url 192.168.137.1:5173/api/device/hello` / `Failed to set URL`。原因不是网络，而是**用户按人类习惯写了 `主机:端口`，而 ESP-IDF 的 HTTP 客户端要求完整 URL（必须有 scheme）**，它直接拒绝解析——设备照样联网、照样轮询，只是每次请求在解析阶段就死掉。
- 顺带暴露第二个易错点：端口写成了 **5173（Vite 前端开发服务器）而不是 8787（Worker API）**。两个端口都在同一台电脑上，占位符和文档若不写清楚，几乎必然被填错一次。
- 修法：**在写入时规范化，而不是在读取时报错**——保存服务器地址时若不含 `://` 就补 `http://`（已有 scheme 的原样保留，https 同理），并在页面提示里写明"填 Worker 地址，5173 不是它"。这类"用户会按习惯写、机器却要求严格格式"的字段，接纳习惯比要求用户记住格式更省事。
- 通用规则：**报错信息里的关键词往往已经指出了层次**。`Error parse url` 是"字符串格式"层，不是"网络/防火墙/域名"层；把它先读成格式问题，可以省掉一整轮网络排查。
- 同时修正一条此前的推断：本轮日志显示设备**已经联网**（能主动向控制台发起 `/api/device/hello`），所以"点按进配网＝设备没连上"这一判断在当时的时刻成立、但已不再是当前状态；当前故障是**地址写法**，不是连接。排查时要用最新日志覆盖旧推断，不要沿用上一个结论。
## 配置值的"规范化"必须同时做在写入端与读取端（2026-10-14 服务器地址补 scheme）
- 第一版只在**保存时**把 `192.168.137.1:8787` 补成 `http://192.168.137.1:8787`。用户重烧后同样的 `Error parse url 192.168.137.1:8787/api/device/hello` 又出现了——因为 **NVS 里那条旧值不会因为换固件而改变**，写入端的补全只对"以后新保存的值"生效。
- 这是所有"修正输入格式"类改动的通病：**只补写入端＝只治新数据，存量数据必须靠再操作一次才会好**；而用户不会知道"要再去保存一次"，于是看起来像修复没生效。正确做法是**两端都做**：写入端规范化让存储保持干净，读取端（这里是 `robot_cloud_init` 使用地址前）再规范化一次，让旧值自愈。两处规则要一致——本项目在注释里互相指了对方（`robot_network.c` 的 `normalize_server()` ↔ `robot_cloud.c` 的 `normalize_base_url()`）。
- 默认值不要一律取 `http://`：本项目按"IP 字面量或无点主机名＝局域网 → `http://`；其它名字 → `https://`"分流。上线后的域名几乎只可能是 https，把 `desk.example.com` 补成 http 会撞上重定向或直接失败，比原始报错更难查。
- 工具链补记：本项目"用 `compile_commands.json` 单文件编译校验"的做法对 **含 `-DXXX=\"...\"` 的宏定义会二次转义**（PowerShell 传参时又会转义一层）。此前一直没暴露，是因为出问题的宏（`MBEDTLS_CONFIG_FILE`）只在包含 mbedtls 头文件的文件里才被用到；这次编 `robot_cloud.c`/`robot_voice.c` 就报 `#include expects "FILENAME"`。判断依据仍是"报错与被改动的部分没有因果"。稳妥做法：**把 CMake 记录的原始命令行写进 .bat，用 `cmd /c` 执行**，让 shell 按生成时的规则解析，而不是自己分词。
## "识别断断续续"要先分清是采集碎、说话停、还是识别在分句（2026-10-14）
- 用户反馈语音识别"断断续续"，转写结果是"你。能听见。我说话。吗？"，机器人还顺着这句话吐槽了一通。这类反馈最容易把人带偏：**转写里的句号有三种完全不同的来源**——①音频里真实的停顿（说话节奏）；②识别服务自己的分句（`enable_punc`/DDC 与它的 VAD）；③采集丢帧造成的空洞。三者修法完全不同（分别对应调说话/环境、调服务端请求参数、修采集链路），而"看转写"本身分不出是哪一种。
- 因此先加**可区分证据**再改代码：`robot_voice.c` 在每轮录音结束打印一行 `capture report`，含 ①`audio/wall`——缓冲区里的音频时长 vs 从开始录音到结束的墙钟时长（两者接近＝采集没丢帧）；②`voiced ms`——按当前阈值判定为"有声"的时长；③`longest mid-speech gap` 与 `gaps >= 400 ms` 个数——**只统计后面还接着语音的静音段**，尾部静音不计，因此这一项就是"识别端不得不据此断句"的直接度量。三种读数各自指向一种修法。
- 顺带查出一个真实的配置陷阱：用户 `sdkconfig` 里 `ROBOT_CLOUD_VOICE_THRESHOLD=320`，而 Kconfig 默认值与实测结论是 700（320 是当年增益高 16 倍时选的）。**改 Kconfig 的 `default` 只影响新生成的 sdkconfig，已存在的 sdkconfig 会一直保留旧值**——所以"我把默认值改对了"不等于设备上生效。凡是靠 Kconfig 传递的调参项（阈值、增益、采样率），都要去设备上的 `sdkconfig` 核对实际值，而不是只看 Kconfig 文件。
- 另一条经验：**用户听到的"设备表现"，有时只是模型在复述它看到的文本**。这一轮机器人回复"你咋个说话断断续续的嘛"，其实是模型看到了带句号的转写；把它当成"设备自己在断"会让排查方向跑偏。判断依据应当来自设备侧的测量数据，而不是对话内容。
## 断句发生在哪里：设备只判断"说完了"，标点属于识别服务（2026-10-14）
- 用户问"哪里有检测断句的"。答案分两层：①**设备侧没有任何标点或断句逻辑**——`robot_voice.c` 只用能量阈值判断"说完了"（`silence_threshold` 700 与 `silence_stop_ms` 900 的尾静音），并把整段 PCM 一次性 POST 上去；②**断句发生在服务端请求里**——`server/voice/volc.ts` 向火山 ASR 声明 `enable_punc: true`（标点）、`enable_ddc: true`（语义顺滑）、`show_utterances: true`（返回它自己的分段），火山按它检测到的静音切句。所以"介绍。1下。你自己。"是火山对音频的判断结果，不是设备输出的。
- 因此排查这类问题**必须拿音频本身的证据**，而不是看转写"像不像"。本轮 `capture report` 正好给了证据：`5840 ms of audio over 5870 ms wall`（差 0.5%，没有丢帧）＋ `longest mid-speech gap 860 ms, gaps >= 400 ms: 2`——音频里真有两段长静音，火山的断句是对的。

## 用日志时间戳证明一个竞态：唤醒提示音被录进了句子（2026-10-14）
- 证据链条：`playback stream start`(90518) → 我们的录音起点（≈90528，由 96398 的 capture report 反推）→ 300 ms 后麦克风峰值 `20271`（很响，正是提示音）→ 随后 860 ms 静音 → 才轮到说话。
- 结论：**"等提示音播完再开始录"这段代码没等住**。唤醒路径是先起提示音、紧接着就叫云端录一轮，而我们判断"是否还在播"时提示音可能**还没开始**，"当前没在播"于是被当成"可以开始录"——典型的竞态。
- 修法（两层，互为兜底）：①麦克风旁路里**丢弃提示音还在播时的帧**（`robot_audio_is_playing()` 为真就跳过），提示音根本进不了录音；②录音结束后**裁掉首尾静音**（保留 150 ms / 250 ms 余量），把"等提示音那段空白"也去掉。两者都只作用于我们自己的云端通道（`robot_voice.c`），不碰 `robot_audio`／`robot_wakeup` 的既有行为。
- 通用经验：**"等待某个异步状态"必须先确认那个状态出现过**，否则"尚未开始"和"已经结束"无法区分——`while (busy) wait;` 在"启动有延迟"时等于没等。判断依据来自时间戳（谁先谁后），不是来自代码"读起来应该没问题"。
## 转写里的"。"：先量音频，再决定改哪里（2026-10-14 复测）
- 复测数据（两轮）：`4800 ms of audio over 4799 ms wall`／`4840 ms of audio over 4839 ms wall`——采集完整、无丢帧；`longest mid-speech gap 760 / 580 ms, gaps >= 400 ms: 1`；`trimmed 690 / 1080 ms`（首尾裁剪生效）；转写分别是"你。能帮我。做哪些工作？"与"那你。给我介绍。一下哈尔滨。"——**断句位置与那处长静音一一对应**。
- 另一条旁证：`robot_audio` 的 `capture_paused` 是"干脆不喂帧"，不是"喂静音"，所以任何采集暂停都会让 `audio/wall` 变小；这两轮两者相等，说明既没丢帧也没暂停——那段静音是房间里的真实安静。

- 记这条的重点是**判断顺序**：先量 `audio/wall`（是否丢帧）、再量 gap 统计（音频里有没有长静音）、最后才决定是在采集端修、在音频预处理修、还是在识别参数上修。数据不到位时，三个方向都会看起来同样合理。
- 另记一处待评估（本轮未改）：请求里的 `enable_itn: true` 把"一下"转成了"1下"（`heard: 介绍。1下。你自己。`）。ITN 对数字与日期有用，但会对口语量词产生这种副作用；若要关，必须在真实服务上重新验证后再定，不能凭猜。
## "取消一个流式会话"不能只清空本地队列（2026-10-15）
- 现象：机器人说长回答时按一次 BOOT，它"跳过一段继续说剩下的"，要按好几遍才停。
- 根因：云端一轮的回复是**边收边播**的流——本地播放队列只是缓冲区。按一次键执行的是 `robot_audio_abort_playback()`（丢掉已缓冲的音频），但 HTTP 流仍在到达、被解析、被继续播放。观感因此是"跳一段、接着说"，按几次跳几段，直到流自己结束。
- 规则：**取消一个正在流式接收的会话，必须同时做两件事**——①停止投喂（置取消标志，必要时关闭连接），否则数据源源不断；②丢弃本地已缓冲的输出，否则已进队列的部分还会播完。只做②就是本次的现象；只做①则"数据停了但已排队的声音还在响"。
- 实现（`robot_voice.c` ＋ `robot_app.cpp`）：新增 `robot_voice_cancel()`（忙时同时置 `stop_requested` 与 `cancel_requested`）；读取循环在每次读之前检查取消标志，取消时 `abort_playback()`、结束播放、恢复采集并返回 `ESP_ERR_INVALID_STATE`，`last_result` 记为"已取消"（控制台指令记录可见）；录音阶段取消则直接不上传；每轮开始时清掉残留标志。`robot_app` 的按键路径在云端一轮进行中调用它并**立即**丢弃已排队音频，声音当场停、流在下一个 chunk 到达时终止；录音阶段的按键也不再被当成"唤醒"吞掉。
- 附注：`esp_http_client_read` 是阻塞的，所以"流真正断掉"的时刻取决于当前这次读何时返回（服务端按句下发，通常很快）。要做到"按下即断流"得让读操作可中断（异步关闭连接或改成分片轮询），本轮没有引入这种复杂度——观感上"立即静音 ＋ 随后停止"已经解决了用户的问题。**能停下来的关键不是更快的 abort，而是让数据源也停下来。**
## "部署成功"不等于"能访问"：先验证可达性再宣布上线（2026-10-15）
- 现象：`wrangler deploy` 完整成功（Worker、绑定、版本号、静态资源全部就绪），但从同一台机器 `curl` 部署出来的地址却是 `http=000` + `Could not connect`。
- 定位方式（值得记住的三步）：①`curl -sS --max-time N -w "%{http_code}"` 拿到明确失败而不是"没输出"；②`Resolve-DnsName` 看解析结果——`aidesk-console.<account>.workers.dev` 被解析成 **Facebook 的 IP**（`31.13.85.34`、`...face:b00c...`），这是**DNS 污染的特征**（把被阻断的域名解析到无关的境外 IP）；③**用对照域名排除本机网络故障**——同一时刻 `https://www.cloudflare.com/` 返回 200，说明外网是通的、被拦的是 `workers.dev` 这个域。
- 结论：`*.workers.dev` 在国内网络基本不可用（DNS 污染＋连接阻断）。**Cloudflare Workers 的部署成功率与它在目标网络的可达性完全无关**；产品面向国内用户时，必须准备自定义域名（把自有域名接入 Cloudflare 再绑 Worker）或换用国内可达的托管。
- 由此得到一条通用规则：**部署类任务的验收标准必须包含"从目标网络实际取到 200"**，而不是"CLI 打印了 Success"。本项目在 T018/T023 上已经建立过同类习惯（"本地通过不等于已部署，部署成功不等于线上已验证"），这次把它具体化为"部署后立刻用 curl 对照验证可达性"。

## 单文件编译通过 ≠ 能链接：移除子系统后必须跑一次完整构建（2026-10-15 T028-7）

## 改 `wrangler.jsonc` 的 `database_id` 会换掉本地 D1 文件（2026-10-15）
- 现象：为了让云端部署可用，把 D1 的占位 ID 换成真实 ID 之后，本机 `wrangler dev` 的**所有接口都 500**——连 `GET /api/auth/me` 这种不查库的业务都在中间件阶段失败。

## 备份文件要“真回灌一次”才算验证过（2026-10-15 D1 快照）

## 记忆文档是混合换行，按 CRLF 切行会「整段找不到」（2026-10-15）
- 现象：脚本按 `t.split("\r
")` 取行后查找「以某条任务开头的行」，断言 `bullet not found`——但 `Select-String` 明明能搜到。

## 「防抖」不等于「松手」：微调控件必须等 pointerup（2026-10-15 音量滑杆）
- 第一版把 350 ms 防抖挂在 `onChange` 上，自以为实现了"松手即下发"。用户复测立刻抓到反例：**按住鼠标不动停顿一下也会触发**——正是微调（61→59→60）时最痛的地方，一次刷出三条指令。
- 正确做法：用指针事件区分"在拖"和"松手"。`onPointerDown` 里 `setPointerCapture(e.pointerId)`（关键：鼠标移出控件后 `pointerup` 仍会回到该元素）并置 `dragging=true`；`onPointerUp`／`onLostPointerCapture` 才真正提交；`onChange` 在拖动期间**只更新显示**；键盘等非指针来源（`dragging` 为假）仍走防抖。再叠一层"与上次提交值相同就不提交"的去重。
- 教训：涉及"连续取值 + 提交一次"的控件（滑杆、颜色选择器、拖动排序），**提交时机要绑在结束事件上，不要绑在"值变了 + 定时器"上**；后者在"停顿但不松手"时必然误发。
## 脚本写文档：`t += t` 会把整份文件复制一遍（2026-10-15）

## 单麦无 AEC 的机器人要不要"边听边说"（2026-10-15 T030 打断）
- 半双工（说话时关麦）不是疏忽，是**单麦无回声消除**下的保守选择：机器人听到自己的声音就可能把自己"唤醒"，形成自激。代价是**用户喊什么都打断不了它**，只能按键。
- 打开打断要同时动三处，缺一处都无效：①播放期间不 `set_capture_paused(true)`；②开一轮时不再 `robot_wakeup_stop()`；③`PcmConsumer` 在对话态也喂唤醒引擎。任一处保持原样，结果都是"喊了没反应"，而日志上完全看不出来。
- 打断的语义要分清：**唤醒词打断 = 切断回复并继续听下一句**（restart），**按键打断 = 取消并结束这段对话**（cancel）。实现上是同一对 stop/cancel 标志再加一个 restart 标志，`voice_run_turn()` 的循环据 restart 决定 continue 还是 break。
- 只在"机器人正在说话"时才接受唤醒词打断：它正在聆听时，用户说的话本来就在录，再打断只会把录音重开一次。

## "恢复动作写在错误分支里"：成功路径反而没人收拾（2026-10-15 T031）
- 典型形状：先 `pause()`，再做一个可能失败的操作，然后**只在失败时 `resume()`**：
  ```c
  robot_audio_set_capture_paused(true);
  err = play_prompt();
  if (err != ESP_OK) { robot_audio_set_capture_paused(false); }   // ← 成功时没人恢复
  ```
  于是**正常路径**留下一个永久生效的副作用。本次后果：重启后麦克风一直停摆，唤醒引擎 armed 却没数据，必须先按一次 BOOT（那条路径里有人调 `set_capture_paused(false)`）才恢复——一个"只有重启后第一次不灵"的诡异现象。
- 审这类代码只要问一句：**"成功路径上，谁来把状态恢复回去？"** 若答不上来，就是 bug。写入端与恢复端要成对出现，且恢复端通常在 finally / 函数末尾**无条件**执行。
- 这类 bug 的日志特征：**什么都看不出来**。相关模块的"就绪"日志照常打印（因为就绪条件确实满足），坏掉的是数据流（没有帧进来）。所以排查"某功能一动不动"时，除了看状态标志，还要看**数据是否真的在流动**（本次的判据就是"待机时串口有没有 `microphone peak=`"）。
- 用户描述里"必须先按一次 X 才生效"几乎是这类 bug 的签名：说明有一处初始化只存在于 X 的路径里。
## 「等它播完」不能只看 `is_playing`：预缓冲窗口里它是 false（2026-10-15）
- `robot_audio_is_playing()` 只在播放任务**攒够预缓冲、真正开始写 I2S** 之后才为真。PCM 刚入队、正在等预缓冲的那几百毫秒里它是 **false**——用"它没有在播"当作"上一轮结束了"就会踩空：本轮录音抢在上一轮开播之前开始。
- 症状很隐蔽：日志上 `answer:` 之后 80 ms 就出现"开始听下一句"，随后一次录音报表是 `0 ms of audio over 10039 ms wall`（一帧都没进来，因为播放期间的帧被 tap 丢弃），接着 4 秒静音超时**在回复还在播的时候**结束了整段对话。
- 正确判据要把"还没开播但已入队"算进去：`is_playing() || playback_buffered_samples() > 0`。凡是用"某资源空闲"当同步条件，都要问一句：**"它有没有可能只是还没开始忙？"**
- 配套教训：把"结束条件"只放在某个回调里（本次是采集回调里的静音超时）是脆的——回调不跑就不会结束。主循环里要有一份**基于时间的兜底**。
## 单麦无 AEC：不要指望"调低阈值"就能实现唤醒词打断（2026-10-15 真机数据）
- 播放期间麦克风电平实测 **9k–26k**（喇叭就挨着麦克风），用户语音被压在里面；同一台设备在安静环境下喊同一句，MultiNet 的 `prob` 只有 **0.300 / 0.653**（阈值 0.20）。信噪比不够时，降低阈值只会制造误触发，不会让被淹没的语音被识别出来。
- 想"边听边说"只有一条正路：**AEC**——用正在播放的 PCM 当参考信号，把它从麦克风信号里扣掉（ESP-SR 的 AFE 提供 `aec_init`，需要把播放数据喂成参考）。没有 AEC 时，半双工（说话时闭麦）+ 按键打断才是诚实的方案。
- 顺带一条判据：**`capture report` 是判断"录音到底有没有在工作"的最佳工具**——`audio ≈ wall` 说明没丢帧；`0 ms of audio over 10039 ms wall` 说明全程被丢弃（通常是"以为没在播、其实在播"或采集被暂停）。
- **决策记录（2026-10-15）**：面对这个上限，用户选择 **B —— 只保留按键（BOOT）打断**，`ROBOT_CLOUD_VOICE_BARGE_IN` 默认关闭（连续对话保留）。要做真打断，前置条件是先给唤醒引擎加 **AEC**（ESP-SR AFE + 播放 PCM 参考），而不是调阈值。
## 改"设备级配置"必须能回退：坏配置不能把设备变成砖（2026-10-15 T032 自定义唤醒词）

## 提前返回的分支也要写"失败原因"，否则调用方的日志只剩一个空冒号（2026-10-15 开机提示音）
- `robot_voice_say()` 有三处提前返回（通道没启动／文本为空／正在对话），它们直接 `return` 而**没有写 `last_result`**；调用方只打印了 `robot_voice_last_result()`，于是真机日志给出 `cloud ready prompt unavailable: `——**冒号后面空的**，等于什么都没说。
- 两条通用做法：①**凡是"对外报告结果"的字段，要在所有返回路径上都写**（含最早的参数校验分支）；②调用方打印时**同时带上错误码**（`esp_err_to_name(err)`）——错误码永远存在，字符串可能没被赋值。只依赖字符串 ⇒ 关键路径上的失败会变成"无法诊断"。

## 两条启动路径之间的先后顺序：不要假设，要发布"就绪"再等（2026-10-15 开机提示音）
- 现象：提示音第一次开口必然失败（`cloud ready prompt attempt 1 failed: ESP_ERR_INVALID_STATE (语音通道未启动)`），0.8 秒后重试才成功。日志时间线显示：提示音任务在 **6661 ms** 开跑，而语音通道在 **6691 ms** 才 `voice channel ready`——**同一台设备上两条启动路径相差约 30 ms，而且先后不保证**（提示音走 TIME_READY 路径，语音通道走 GOT_IP 路径）。
- 教训：**跨路径的初始化顺序不能靠"我算过应该先 A 后 B"**。要在被依赖的一方暴露一个**就绪判据**（本次新增 `robot_voice_ready()`），使用方**有界等待**它（3 s 上限、50 ms 一探）再干活。失败重试能兜住，但会把"顺序问题"伪装成"偶发失败"，还白等一个退避周期。
- 复用检查法：凡是"A 的功能需要 B 先初始化"，先问①A、B 是否在同一条路径上？②不同路径时有没有就绪判据？③等待有没有上限（避免依赖缺失时挂死）？
## 经代理推送时可能报 `cannot lock ref`，但提交其实已经落地（2026-10-15）
- 现象：`git push` 走本机代理（`http://127.0.0.1:7897`）返回 `! [remote rejected] main -> main (cannot lock ref 'refs/heads/main': is at 0239873… but expected 3f7e00b…)`，看起来像被拒绝。
- 核实：`git ls-remote origin refs/heads/main` 直接读服务器 —— **远端已经是 0239873（正是这次要推的提交）**；`git fetch` 后 `## main...origin/main` 同步。即：**推送成功，只是客户端收到了过期的 ref 期望错误**（代理重发 POST 之类的行为会产生同样现象）。
- 纪律：**推送报错先核实远端**（`git ls-remote` 或 `git fetch` + `git status -sb`），确认没上去再重推。盲目重推会把同一批提交再走一遍，还可能叠加出更难看的冲突。
## 「当前状态」字段要问一句：它什么时候被更新？（2026-10-15 控制台「设备当前」不刷新）
- 现象：控制台下发新唤醒词后，「设备当前」长时间不变；而前端其实每 3 秒就在轮询。根因在写入端——`wake_applied` **只在设备发 `hello` 时更新**，而 `hello` 只在**开机／掉线重连**时发。**读端刷新得再勤，写端不更新也没用。**
- 修法：把「设备亲口确认」的那一刻（指令 ack `status=done`）也当作权威来源写回去。设备说「我设好了」，它说的就是当前值——比任何周期性上报都更准、更快，而且不需要改固件。
- 通用检查法：设计任何 `xxx_current` / `last_xxx` 字段时先问三句——①**谁**写它？②**什么时机**写？③用户看到它变旧时会不会误判成「功能坏了」？如果答案是「只在启动时写一次」，那它必然过期；应补上「变更确认」这条写入路径。
## 「等得久」先量再改，而且日志本身可能是错的（2026-10-15 语音延迟）
- 我们的第一反应是"模型慢"——因为设备日志里 `heard:`（识别完）到 `answer:`（回复文本）之间是 4.3 s，另一轮甚至 31 s。**读代码才发现 `reply` 事件是最后才发的**（等所有 TTS 播完），所以那个差值其实是"模型 + 整段合成"，不是首句延迟。**先把日志修对，再谈优化。**
- 可复制的测量手法：**在本地库临时插一台测量用设备**（自己算 `key_hash`、绑已有语音角色），拿一段真实语音直接打 `/api/device/voice`，然后**按帧解析响应流给每个事件打时间戳**。不碰真机、可重复、A/B 对比非常干净；一次只花一轮 API 额度。比"让用户说一句话再看日志"快得多，也准得多。
- 这一轮的收益结构很有代表性：**模型"话多"既是延迟问题也是体验问题**。同一句提问，模型给了一篇编号长文 → 首句慢、整轮 26 s、机器人要念 66 秒语音；加一句"用一到两句口语化的话回答，不要分点"之后，首块音频 7.97 s → **5.23 s**、整轮 26.2 s → **7.06 s**、输出语音 66 s → **7.6 s**。**给下游是"听着"的链路单独约束输出长度，比事后优化传输更划算。**
- 两个小坑也记一下：设备码是 Crockford 字母表（**没有 I/L/O/U**），自己造 key 时写了 O 会被规范化成 0 → 401；测量设备没有 `role_id` → 409（服务端如实拒绝，这正是它该做的）。
## `workers.dev` 被污染，但 `trycloudflare.com` 在国内能直连（2026-10-15 汇报应急）
- 两者都是 Cloudflare 的域名，待遇却不同：`*.workers.dev` 被 DNS 污染（解析到 Facebook/别的 IP，连接超时），而 **`trycloudflare.com` 解析正常**（104.16.x，HTTPS 200）——所以"Cloudflare 在国内不可用"这个笼统印象是错的，要按域名逐个实测。
- 于是多了一条"今天就能用"的应急路径：`cloudflared tunnel --url http://127.0.0.1:8787`（快速隧道，无需账号、无需域名）→ 拿到 `https://<随机词>.trycloudflare.com`。代价是**临时性**：进程一停即失效、重启换地址，所以适合演示兜底，不适合当正式入口。
- 判据纪律：判断"某个域名国内能不能用"，要**分别测 DNS 与连接**（`Resolve-DnsName` + 不带代理的 `curl`），而不是凭平台下结论。
## 判断"国内能不能访问"要用"同 IP、同刻、换 SNI"的对照实验（2026-10-15 域名上线实测）
- 事实链：域名接入 Cloudflare 后（`aideskrobot.xin`，zone active、NS 正确），国内直连只有 **7/10** 成功、耗时 1~13 s 抖得厉害。**先别急着怀疑 Cloudflare 或 IP**：拿同一台 Cloudflare IP，同刻分别用三个 SNI 各打 6 次 —— `www.cloudflare.com` **6/6**、`aideskrobot.xin` **3/6**、`*.trycloudflare.com` **6/6**。三行数据把范围一次锁死：**IP 没问题、Cloudflare 没问题，是这个主机名（大概率 `.xin` 后缀）被针对性干扰。**
- 这条对照法值得复用：**控制变量（同一 IP）＋同一时刻＋只改一个变量（SNI）**。只测一个域名会把网络抖动误判成"域名方案失败"；只测一个 IP 会把"主机名被干扰"误判成"Cloudflare 在国内不可用"。
- 顺带修正一个更早的乐观判断：我们原本认为"换个自己的域名就能绕开 `workers.dev` 的污染"。**绕开污染是真的（DNS 正常解析了）**，但"能解析"≠"能稳定连上"——**可达性要分两层验证：DNS 层、传输层**。
- 工程结论：给国内交付时，**不要把"接了个域名"当成公网可达性的终点**；要么准备就近托管/备案路线，要么按"局域网为主、公网为辅"设计。
## 补记：子域名救不了"后缀被干扰"，而且干扰强度会随时间变（2026-10-15）
- 顺着上一条的 SNI 对照法往下试：给 Worker 加 `robot.aideskrobot.xin` 后同刻对照 —— 裸域名 **0/4**、子域名 **0/4**、隧道 **4/4**，两者解析到同一批 IP ⇒ **干扰作用在后缀（`.xin`）这一层，换子域名无效**。可见"换个子域名试试"只能排除"主机名被点名"这一种假设，**不能解决后缀级问题**。
- 另一条更值得警惕的观察：同一个域名在同一天内 **0/4 → 3/6 → 7/10** 反复波动。**只测一次就下结论，会得到完全相反的判断**（早先那次 7/10 让人以为"能用但不稳"，实际它在某些窗口是完全不通的）。
- 纪律：①判定可达性一律"**同刻、同 IP、单变量**"对照，跨时刻数据不可比；②结论要附上时间窗口与样本量；③**给"演示/交付"选路径时按最差窗口而不是平均值来设计**（因此机器人走局域网、公网只作辅助）。

## 并发"没有 Docker 也要交付容器"：把平台能力收敛到适配层（2026-10-15 T034）
`server/**` 里 20 多个文件之所以能一行不改地跑在 Node 上，是因为它们只依赖三个平台能力：`env.DB`、`crypto`、`fetch`。迁移时的正确动作不是"重写业务层"，而是**把平台差异全部收进适配层**：D1 → `node:sqlite` 的最小包装、ASR 的 `ws` 实现 + 注入点、静态资源读盘。判断标准很简单——**业务文件在 diff 里出现就是设计错了**（本轮 `server/index.ts`／`device-routes.ts`／`voice/*.ts` 的 diff 为空）。

## `fetch` + `Upgrade` 拿 WebSocket 是 Workers 专有语义，Node 里必须换 `ws`（2026-10-15 T034）
同一份端点、同一份帧协议，但建连方式不通用：Workers 用 `fetch(url, {headers:{Upgrade:'websocket'}})` 拿到 `response.webSocket`（所以 URL 要写 `https://`，写 `wss://` 反而会被 Fetch API 拒绝）；Node 只能用 `ws`（`new WebSocket(url, {headers})` 才能带鉴权头，全局 `WebSocket` 不支持自定义头，所以用不了）。**好处**：既然帧编解码在 `server/voice/frames.ts` 里，两个实现共用同一份协议代码，只有"怎么建连"不同——这也是当初把帧协议单独抽出来的价值。**验证方式（拿不到真 key 也能验）**：用假 key 建连 → 607 ms 收到 `Unexpected server response: 401`，证明 DNS/TLS／握手／鉴权头这条路是通的，剩下的只是凭据问题（真 key + 真语音仍未验证，已在 PROGRESS 里记为未验证）。

## `ws` 的 exports 没有 types 条件：装 `@types/ws` 也救不了 `moduleResolution: bundler`（2026-10-15 T034）
`ws/package.json` 的 `exports["."]` 是 `{browser, import: ./wrapper.mjs, require: ./index.js}`，**没有 `types` 条件**，而 ws 自身不带类型；`moduleResolution: "bundler"` 会照着 exports 解析到 `wrapper.mjs`，于是报 `TS7016`。**不要**以为装上 `@types/ws` 就好了——TS 不会在 exports 命中后回落到 `@types`。本轮的做法是在仓库里写 `types/ws.d.ts`，**只声明实际用到的表面**（构造函数带 `headers`、`on('open'|'message'|'close'|'error')`、`send`、`close`）：比 `any` 严（写错方法名立刻编译失败），也不必为类型再引一个依赖。

## 静态资源服务：`有扩展名却找不到` 要 404，不要回落 `index.html`（2026-10-15 T034）
SPA 兜底（`not_found_handling: single-page-application`）的常见实现是"文件不存在就返回 index.html"。这会把**拼错的资源路径**变成一段 HTML：浏览器报 `Unexpected token '<'`，看起来像"JS 语法错误"，实际是取文件取错了。正确做法是按路径形状分流：**没有扩展名**（`/devices/123`）才当路由回落 `index.html`；**有扩展名**（`/assets/x.js`）就当资源，找不到就 404。

## 迁移的"证据链"应该跑在**接口层**，而不是看日志（2026-10-15 T034）
换运行时最怕"看起来起来了，其实某些 SQL 变了行为"。本轮本地验证不是"打开首页看一眼"，而是用一次性账号跑完整链路：注册 → 建模型 → 建角色 → 建设备 → 设备 `hello`（设备鉴权头 + `hash()` 路径）→ 控制台下发唤醒词（`pinyin` 转换）→ 设备拉指令 → ack → `wake_applied` 立即更新 → 清理。**这一串同时覆盖了 D1 包装里最容易出问题的三处**：`INSERT … RETURNING`（限流用的 `first()` 单行返回）、`batch()` 事务、`run()` 的 `meta.changes`。另外，验证 HTTP **非 GET** 请求时必须带 `Origin` 头——CSRF 中间件会先判来源，不带就 403，容易误判成"接口坏了"。
